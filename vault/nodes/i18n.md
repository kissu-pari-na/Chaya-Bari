The whole UI is bilingual. Bangla is the default, and an always-visible switch
in the header changes the language. UI strings are written inline as
`t('বাংলা', 'English')`. Admin-entered content has optional English twins
(`nameEnglish` …) and is shown with `tc()` or `lc()`, falling back to
whichever language exists.

## Rules
- **R-I18N-001** [must] Bangla (`bn`) is the default language. The switch is always visible in the header on every surface: customer, admin and kitchen.
- **R-I18N-002** [must] Every user-visible string has both a Bangla and an English variant: `t(bn, en)` in components, and bilingual message keys for notifications and emails.
- **R-I18N-003** [must] Admin content with an English twin is rendered with `tc` or `lc`. Show the active language's value when present, otherwise whichever exists. Never show an empty label.
- **R-I18N-004** [must] Notifications are stored as a message key plus params (with a Bangla fallback) so the bell renders in the reader's current language, not the language that was active when the notification was created.
- **R-I18N-005** [should] Numbers and money shown in Bangla use Bengali digits (`toBnDigits`, `formatBdt`).
- **R-I18N-006** [must] The language choice persists in localStorage and is mirrored into the i18n module during the same render, so plain helpers never lag one render behind.

## Decisions
- **D-I18N-001** [confirmed 2026-09-19] Localize notifications to follow the language toggle (commit 7abde6d).
  Why: a Bangla notification read by an English-preferring user (or the reverse) was confusing. Storing key + params makes the text follow the reader.

## Ideas
- **I-I18N-001** [new · impact:med · effort:S] Detect the browser's language on the very first visit and pre-select English for non-Bangla browsers, while keeping Bangla as the default for everyone else.
